# PHP実装の解析: `webapp/php/index.php`

このドキュメントは、ISUCONウェブアプリケーションのPHP実装のエントリポイントである `webapp/php/index.php` ファイルを解析したものです。

## 1. 概要と主要技術

このアプリケーションは、PHPのマイクロフレームワークである **Slim Framework (バージョン4)** を使用しており、依存性注入のために **PHP-DI (Container)** を活用しています。依存性の管理には **Composer** が使われています。

## 2. 静的ファイルの提供 (開発時)

`index.php` の冒頭のブロックには、PHPの組み込み開発サーバーが使用されている場合に、`/public` ディレクトリから直接静的アセット (JavaScript、CSS、ICOファイル) を提供するロジックが含まれています。これはローカル開発を簡素化するための一般的なパターンですが、本番環境では通常、専用のウェブサーバー (Nginxなど、`compose.yml`で設定されている通り) によって処理されます。

## 3. 定数と設定

*   **`POSTS_PER_PAGE`**: `20` に定義されており、1ページあたりの投稿数を表します。
*   **`UPLOAD_LIMIT`**: `10 * 1024 * 1024` バイト (10 MB) に設定されており、アップロード可能な画像ファイルの最大サイズを制限しています。
*   **セッション管理 (Memcached)**:
    *   PHPのセッションストレージは `memcached` を使用するように設定されています。
    *   Memcachedサーバーのアドレスは、`ISUCONP_MEMCACHED_ADDRESS` 環境変数から取得されるか、デフォルト値として `127.0.0.1:11211` が使用されます。
    *   セッションを開始するために `session_start()` が呼び出されます。
*   **データベース設定**:
    *   データベース接続パラメーター (ホスト、ポート、ユーザー名、パスワード、データベース名) は、環境変数 (例: `ISUCONP_DB_HOST`) から取得されるか、デフォルト値にフォールバックします。これらの設定は依存性注入コンテナ内で管理されます。

## 4. 依存性注入 (DI) コンテナのセットアップ

アプリケーションはPHP-DIを使用してサービスと設定を管理しています。コンテナ内で定義されている主要なサービスは以下の通りです。

*   **`settings`**: `public_folder` パスやデータベース接続の詳細など、アプリケーション全体の設定を提供します。
*   **`db`**: MySQLデータベースと対話するための `PDO` オブジェクトのインスタンスです。`settings` サービスからの設定で構成されます。
*   **`view`**: PHPテンプレートファイルをレンダリングする役割を担う `Slim\Views\PhpRenderer` のインスタンスです。`views` ディレクトリを使用するように構成されており、すべてのレンダリングされるページに共通の `layout.php` テンプレートを自動的に適用します。
*   **`flash`**: 一時的なフラッシュメッセージを管理・表示するための `Slim\Flash\Messages` のインスタンスです。
*   **`helper`**: 頻繁に使用されるアプリケーションロジックとデータベース操作をカプセル化したカスタムヘルパークラス (`new class($c)` ) です。その主要なメソッドは以下の通りです。
    *   `db_initialize()`: 主にベンチマークのための `/initialize` エンドポイントで使用される、特定のテーブル (`users`、`posts`、`comments`) およびユーザーフラグをリセットするSQLコマンドを実行します。
    *   `fetch_first($query, ...$params)`: 準備済みステートメントを実行し、最初の結果行のみを返すユーティリティメソッドです。
    *   `try_login($account_name, $password)`: ユーザーのアカウント名とハッシュ化されたパスワードをデータベースと照合して認証を処理します。
    *   `get_session_user()`: セッションから現在ログインしているユーザーの詳細を取得し、データベースから完全なレコードをフェッチします。
    *   `make_posts(array $results, $options = [])`: 投稿データの配列を処理します。各投稿について、コメント数、限られた数のコメント (または `all_comments` オプションがtrueの場合はすべてのコメント)、および関連するユーザーの詳細をフェッチします。

## 5. グローバルヘルパー関数

アプリケーションのさまざまな側面をサポートするために、いくつかのスタンドアロンヘルパー関数がグローバルに定義されています。

*   `escape_html($h)`: XSS脆弱性を防ぐための `htmlspecialchars` のラッパーです。
*   `redirect(Response $response, $location, $status)`: HTTPリダイレクトを実行するためのユーティリティです。
*   `image_url($post)`: 投稿IDとMIMEタイプに基づいて画像のURL (例: `/image/{id}.jpg`) を構築します。
*   `validate_user($account_name, $password)`: アカウント名 (英数字、アンダースコア、3文字以上) とパスワード (英数字、アンダースコア、6文字以上) の形式を検証します。
*   `digest($src)`, `calculate_salt($account_name)`, `calculate_passhash($account_name, $password)`: ユーザーパスワードを安全にハッシュ化する責任を持つ関数です。これらは、アカウント名から派生したソルトを組み合わせて、`openssl dgst -sha512` を使用してSHA-512ハッシュを生成します。

## 6. 定義されたルート

アプリケーションはSlimのルーティング機能を使用して、ウェブアプリケーションのコア機能を提供するさまざまなエンドポイントを定義しています。これらのルートは、他の言語実装で見られるものとほぼ同じです。

*   **`GET /initialize`**:
    *   `helper->db_initialize()` メソッドを呼び出してデータベースの状態をリセットします。
    *   200 OKの空のレスポンスを返します。
*   **`GET /login`**:
    *   ユーザーがすでにログインしている場合、`/` にリダイレクトします。
    *   `login.php` ビューをレンダリングします。
*   **`POST /login`**:
    *   ユーザーがすでにログインしている場合、`/` にリダイレクトします。
    *   `helper->try_login()` を使用してユーザーのログインを試行します。
    *   成功した場合、`$_SESSION['user']` と `$_SESSION['csrf_token']` を設定し、`/` にリダイレクトします。
    *   失敗した場合、フラッシュメッセージを追加し、`/login` にリダイレクトします。
*   **`GET /register`**:
    *   ユーザーがログインしている場合、`/` にリダイレクトします。
    *   `register.php` ビューをレンダリングします。
*   **`POST /register`**:
    *   ユーザーがログインしている場合、`/` にリダイレクトします。
    *   提供された `account_name` と `password` を `validate_user()` を使用して検証します。
    *   重複する `account_name` がないか確認します。
    *   有効で一意の場合、新しいユーザーをハッシュ化されたパスワードとともに `users` テーブルに挿入します。
    *   `$_SESSION['user']` と `$_SESSION['csrf_token']` を設定し、`/` にリダイレクトします。
    *   検証または一意性の失敗の場合、フラッシュメッセージを追加し、`/register` にリダイレクトします。
*   **`GET /logout`**:
    *   ユーザーセッションデータ (`$_SESSION['user']`、`$_SESSION['csrf_token']`) をクリアします。
    *   `/` にリダイレクトします。
*   **`GET /`**:
    *   現在のセッションユーザーを取得します。
    *   データベースから最近の投稿を取得し、`helper->make_posts()` を使用して処理します。
    *   投稿とユーザー情報を含む `index.php` ビューをレンダリングします。
*   **`GET /posts`**:
    *   オプションの `max_created_at` タイムスタンプ以前に作成された投稿を取得します。
    *   `helper->make_posts()` を使用して投稿を処理します。
    *   `posts.php` ビューをレンダリングします (Rubyの `layout: false` から推測すると、おそらくAJAXエンドポイント)。
*   **`GET /posts/{id}`**:
    *   IDで単一の投稿をフェッチします。
    *   `helper->make_posts(['all_comments' => true])` を使用して投稿とそのすべてのコメントを処理します。
    *   `post.php` ビューをレンダリングします。投稿が見つからない場合は404を返します。
*   **`POST /`**:
    *   ログイン済みのユーザーと有効なCSRFトークンが必要です。
    *   画像アップロードを処理します: MIMEタイプ (JPEG、PNG、GIF) とファイルサイズ (`UPLOAD_LIMIT`) を検証します。
    *   新しい投稿 (画像データを含む) を `posts` テーブルに挿入します。
    *   新しく作成された投稿のページ (`/posts/{pid}`) にリダイレクトします。
    *   検証エラーのためにフラッシュメッセージを追加します。
*   **`GET /image/{id}.{ext}`**:
    *   指定された投稿IDの画像データを取得します。
    *   要求されたファイル拡張子 (`.jpg`、`.png`、`.gif`) を保存されているMIMEタイプと照合して検証します。
    *   `Content-Type` ヘッダーを設定し、生の画像データを出力します。見つからない場合やMIMEタイプが一致しない場合は404を返します。
*   **`POST /comment`**:
    *   ログイン済みのユーザーと有効なCSRFトークンが必要です。
    *   `post_id` が整数であることを検証します。
    *   新しいコメントを `comments` テーブルに挿入します。
    *   投稿のページにリダイレクトします。
*   **`GET /admin/banned`**:
    *   管理者権限 (`authority = 1`) を持つログイン済みユーザーが必要です。
    *   管理者ではない、かつ削除フラグが立っていないユーザー (`del_flg = 0`) のリストをフェッチします。
    *   `banned.php` 管理ビューをレンダリングします。権限がない場合は403を返します。
*   **`POST /admin/banned`**:
    *   管理者権限を持つログイン済みユーザーと有効なCSRFトークンが必要です。
    *   指定されたユーザーID (`uid` パラメーター) の `del_flg` を `1` に更新してユーザーを禁止します。
    *   `/admin/banned` にリダイレクトします。
*   **`GET /@{account_name}`**:
    *   `account_name` でユーザーの詳細をフェッチします。ユーザーが見つからないか禁止されている場合は404を返します。
    *   ユーザーの投稿を取得します。
    *   ユーザーの総コメント数と、ユーザーの投稿に対するコメント数を計算します。後者は、ユーザーが非常に多くの投稿をしている場合、`IN` 句自体が非常に長くなり非効率になる可能性があるため、潜在的に非効率です。
    *   ユーザー、投稿、コメントの統計情報を含む `user.php` ビューをレンダリングします。

## 7. パフォーマンスに関する考慮事項 (N+1 クエリ)

Ruby実装と同様に、このPHP実装もいくつかのN+1クエリパターンを示しており、ISUCONのような高負荷環境では深刻なパフォーマンスボトルネックとなります。

*   **`make_posts()` メソッド**:
    *   初期の結果セット内の各投稿について、以下のための個別のデータベースクエリが実行されます。
        *   その投稿のコメントの `COUNT(*)` を取得する。
        *   コメント自体をフェッチする。
        *   投稿作成者のユーザー詳細 (`SELECT * FROM users`) をフェッチする。
        *   各コメント作成者のユーザー詳細をフェッチする。
    *   これにより、`1 (posts) + N (posts) * [1 (comment_count) + 1 (comments) + 1 (post_user) + M (comments_per_post) * 1 (comment_user)]` というクエリ数になります (Nは投稿数、Mは投稿あたりのコメント数)。
*   **`GET /@{account_name}` ルート**:
    *   `commented_count` をフェッチする際に `IN` 句を使用していますが (個々のクエリよりも優れていますが)、最初にユーザーのすべての投稿IDをフェッチし、ユーザーが非常に多くの投稿をしている場合、`IN` 句自体が非常に長くなり、効率が低下する可能性があります。

これらの領域は、ISUCON競技における主要な最適化ターゲットであり、キャッシュ、非正規化、またはより効率的な単一クエリによるフェッチなどが考えられます。

## 8. セキュリティ側面

*   **CSRF保護**: CSRFトークンが生成され、`POST` リクエストに対して検証されることで、クロスサイトリクエストフォージェリ攻撃を防ぎます。
*   **パスワードハッシュ化**: ユーザーパスワードは平文で保存されません。代わりに、保存と比較の前にSHA-512とソルト (アカウント名から派生) を使用してハッシュ化されます。
*   **SQLインジェクション防止**: パラメータ化されたクエリ (`PDO::prepare()` と `execute()`) を使用することで、SQLロジックをユーザー提供データから分離し、SQLインジェクションの脆弱性を効果的に防ぎます。
*   **ファイルアップロード検証**: 画像のMIMEタイプ (JPEG、PNG、GIF) とファイルサイズに関する基本的な検証が実装されており、ファイルアップロードに関連する一部のセキュリティリスクを軽減します。
*   **ホスト認証**: Slimの `set :host_authorization, { permitted_hosts: [] }` は、Hostヘッダー攻撃を防ぐために使用されます。
